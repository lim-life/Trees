# 种子法

> 这份文档讲三件事:什么算种子,种子怎么写,写完之后它怎么长大。

---

## 1. 种子还是落叶:一个判据

**这次有没有产生「下次还能用的判断」?**

- 有 → 🌰 种子,写进 `forest/seeds/`
- 没有 → 🍂 落叶,只在 `forest/leaves.log` 记一行

拿不准的时候,问自己两个问题:

1. **换一个项目,这条还成立吗?** 只对这个项目成立的,是记录,不是经验。
2. **我能说出它什么时候不该用吗?** 说不出来,说明还没想清楚,先别播。

| 这次发生的事 | 判定 | 理由 |
|---|---|---|
| 换了壁纸 | 落叶 | 没有判断 |
| 打开软件 | 落叶 | 没有判断 |
| 把 `COM3` 改成 `COM5`,烧录成功了 | 落叶 | 只是这台机器的事实 |
| 发现每次烧录前都得先枚举串口,端口号不能写死 | 种子 | 下次烧录还用得上 |
| MSYS 下 Windows 路径报错,改成 `/c/...` 就好了 | 种子 | 同类环境都会再遇到 |

落叶的格式只有一行:

```
2026-10-16 14:32  换壁纸    无复用价值
2026-10-16 15:10  打开软件  无复用价值
```

**为什么落叶不进库**:种子库靠检索起作用。垃圾一多,真正有用的那颗就被淹掉了。宁可少播,不要乱播。

### 同类项目:搬树,不重播

如果已经有一棵同类项目的大树,就直接复用这棵树,不要把它的种子再播一遍。**只有这次新冒出来的想法才单独播种。**

## 2. 三段正文,缺一不可

每颗种子的正文都必须有这三段:

```markdown
## 判据
什么时候该用它

## 做法
怎么做

## 不适用
什么时候别用
```

`## 旁证` 是可选的,用来放原始项目里的具体记录,比如报错原文、文件路径、会话 id。

| 段落 | 作用 | 缺了会怎样 |
|---|---|---|
| 判据 | 让检索知道什么情境下该把它捞出来 | 捞不出来,或者到处乱冒 |
| 做法 | 能直接照着执行 | 只是一句感想,没法用 |
| 不适用 | 划出边界 | **用错地方,而且你自己察觉不到** |

### 为什么「不适用」最值钱

经验在被抽象的时候,最先丢掉的就是边界。

你在项目里学到「用 `/dev/null` 丢弃输出」,当时心里很清楚这是在 MSYS 里。写成种子时,如果只写「丢弃输出用 `/dev/null`」,下次换到原生 PowerShell 照搬,就会出错。这颗种子本身没写错,错在它没说自己在哪儿会失效。

「不适用」还有第二个作用:**它是合成的线索。** 规则 5 里的补位型互补,判据就是「A 的不适用条件正好是 B 的适用场景」:

```
A:MSYS 下丢弃输出用 /dev/null     不适用:原生 PowerShell
B:原生 PowerShell 丢弃输出用 NUL  不适用:MSYS
```

A 和 B 的「不适用」恰好互指,系统能据此认出它们是一对,可以合成成「Windows 下按 shell 类型选空设备」。一颗没写「不适用」的种子,永远凑不成这样的一对。

**写「不适用」的最低要求**:至少写一个具体的环境、条件或反例。不要写「视情况而定」。

## 3. 好种子 vs 烂种子

### 第 1 组:太空泛

❌ 烂:

```markdown
title: 路径要注意格式
## 判据
处理路径的时候
## 做法
注意格式
## 不适用
无
```

✅ 好:

```markdown
---
id: seed-0001
title: MSYS 路径要用 Unix 格式
labels: [Windows, MSYS, bash, 路径]
state: buried
prev_state: null
watered: 0
failed: 0
born: 2026-10-16
last_watered: 2026-10-16
from_tree: hand-sword-radar
from_branch: claude-opus-5-5
origin: native
confidence: 1.0
bloodline: []
synthesized_into: null
evidence: "会话 2026-10-16 构建脚本报错"
---

## 判据
在 Git Bash / MSYS2 里运行脚本,脚本参数里有 Windows 路径(如 `C:\work\a.txt`),报"找不到文件"或反斜杠被吞掉。

## 做法
把路径写成 `/c/work/a.txt`;已有的路径变量用 `cygpath -u "$p"` 转换。

## 不适用
- 原生 PowerShell / cmd:这些环境要用 `C:\...`
- 路径要传给 Windows 原生程序(如某些 .exe 的参数):先用 `cygpath -w` 转回去

## 旁证
`build.sh` 第 12 行,`cp C:\work\a.txt dist/` 报 No such file。
```

差别:好种子的判据带着能对上号的症状,做法可以直接复制执行,不适用写了两个具体反例。

### 第 2 组:把项目事实当经验

❌ 烂:

```markdown
title: 烧录用 COM5
## 判据
烧录固件
## 做法
端口选 COM5
## 不适用
(空)
```

这其实是落叶,换一台机器就不对了。

✅ 好:

```markdown
title: 烧录前先枚举串口,不写死端口号
labels: [串口, 烧录, 嵌入式]

## 判据
脚本或命令里要指定串口烧录固件;换过 USB 口、换过电脑,或者插了多块板子。

## 做法
烧录前先列出当前串口(Linux:`ls /dev/ttyUSB* /dev/ttyACM*`;Windows:设备管理器或 `mode`),按设备描述挑端口,再传给烧录命令。

## 不适用
- 固定工位、端口已在 udev 规则里绑死的产线环境
- 通过网络 / JTAG 烧录,不走串口

## 旁证
本次 COM3 → COM5 才成功,原因是换了 USB 口。
```

「COM5」这个具体事实没有丢,它留在了旁证里。

### 第 3 组:没有边界

❌ 烂:

```markdown
title: 丢弃输出用 /dev/null
## 判据
不想看命令输出
## 做法
`cmd > /dev/null 2>&1`
## 不适用
无
```

✅ 好:

```markdown
title: MSYS 下丢弃输出用 /dev/null
labels: [Windows, MSYS, bash, 输出重定向]

## 判据
在 MSYS / Git Bash 中要静默某条命令。

## 做法
`cmd > /dev/null 2>&1`

## 不适用
- 原生 PowerShell / cmd:用 `NUL`
```

写上「不适用」之后,它就能和「原生 PS 用 NUL」那颗种子配成补位型互补(见 §2)。

### 第 4 组:把一次的感想当规律

❌ 烂:

```markdown
title: gemini 写代码不靠谱
```

一次结果说明不了什么,而且没有做法。模型的表现交给 `trees profile` 从分支数据里统计,不需要手写成种子。

✅ 好:

```markdown
title: 多页演示代码先定共享样式,再分页实现
labels: [前端, 演示, 多页面, 分工]

## 判据
多页(≥5 页)静态演示页面,由多个 AI 或多人分页实现。

## 做法
先产出一份共享的 CSS 变量和组件清单,并在派单说明里写明"只许用清单里的类名",再分页开工。

## 不适用
- 单页面
- 每页本来就要求不同视觉风格(如风格对比稿)

## 旁证
hand-sword-radar 的 impl 分支,14 页样式不统一,outcome: mixed。
```

## 4. 浇水就是证据

种子刚播下时是 `buried`(埋土)。它能不能长大,只看一件事:**有没有被真的用上,并且验证通过。**

```
buried ──浇水 1 次──▶ sprouting ──浇水 ≥2 次──▶ growing ──合成 或 浇水 ≥5 次──▶ advanced

任意状态 ──6 个月未浇水──▶ boxed ──被召唤──▶ 回到原状态(prev_state)
```

- `trees water <id> --ok`:用了而且有效,`watered +1`,`last_watered` 更新为当天
- `trees water <id> --fail`:用了但没效果,`failed +1`
- 只是被检索出来、看了一眼,不算浇水

### 为什么要用够了才往上抽象

- **一次可能是巧合。** 只浇过一次水的种子,可能只在那一个项目里成立。
- **抽象不可逆。** 合成会丢细节,所以铁律要求「合成要人审」。种子越往上合成,离原始证据越远,浇水次数就是你敢往上走的底气。
- **原件不删。** 合成后原种子保留,只标 `synthesized_into: <新id>`。抽象错了还能拆回来。
- **`failed` 同样重要。** 浇水多、失败也多,通常说明「不适用」还没写全。该去补边界,不要急着合成。

### 导入的种子先存疑

从种子包导入的种子:

```yaml
origin: external
confidence: 0.5
```

连续验证成功 3 次后,`confidence` 才升到 1.0。别人的经验,要在你的环境里验证过才算数。

### 入盒不是删除

6 个月没浇水的种子会进入 `forest/box/`,入盒前的状态记在 `prev_state` 里。召唤之后,它回到入盒前的状态,不会从头再长。入盒判据看的是 `last_watered`,不是 `born`。

## 5. 标签怎么写才能命中

检索分两层:**标签精确匹配 + 语义模糊匹配**。标签还决定了种子和谁关联:只共享 1 个标签算低关联,只做邻接标记,不合成。

### 规则

1. **写情境,不写评价。** 用 `Windows`、`MSYS`、`串口`,不用 `重要`、`技巧`、`坑`。
2. **3-5 个为宜。** 太少,检索命中不了;太多,会和所有种子都沾边,关联失去意义。
3. **从三个角度各挑一两个:**
   - 环境:`Windows`、`MSYS`、`PowerShell`、`Node`
   - 对象:`路径`、`串口`、`固件`、`CSS`
   - 动作 / 问题类型:`烧录`、`输出重定向`、`排查`
4. **同一个概念只用一种写法。** 定了 `Windows`,就不要再出现 `win`、`Win10`、`windows`。写新标签之前,先用 `trees find` 看看库里已经在用的写法。
5. **中英文统一。** 专有名词保留原文(`bash`、`MSYS`),通用概念用中文(`路径`、`烧录`)。一个概念不要中英文各写一份。
6. **把边界里的环境也想一遍。** 「不适用」里提到 PowerShell,标签里就要有能区分环境的词(比如 `MSYS`),不能只写一个笼统的 `Windows`。

### 对照

| ❌ | ✅ | 理由 |
|---|---|---|
| `[经验, 重要]` | `[Windows, MSYS, 路径]` | 评价词不描述情境 |
| `[win, Windows, windows]` | `[Windows]` | 重复写法会拆散命中 |
| `[编程]` | `[bash, 输出重定向]` | 太宽,跟谁都关联 |
| `[hand-sword-radar]` | 不放进标签 | 项目归属写在 `from_tree` 里 |

## 6. 播种前自查

- [ ] 换个项目还成立吗?
- [ ] 标题是一句话,能看出做什么
- [ ] 判据里有能对上号的症状或情境
- [ ] 做法可以直接照着执行
- [ ] 不适用里至少有一个具体反例
- [ ] 项目里的具体事实放进了旁证,没有混进做法
- [ ] 标签 3-5 个,写法和库里已有的一致
